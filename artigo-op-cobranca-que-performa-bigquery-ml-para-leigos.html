BigQuery ML, explicado para quem nunca o usou

Treinar e usar um modelo com comandos de SQL, dentro do banco de dados em que as cobranças já estão: o arquivo de exemplo, cada comando com o código e o resultado, e telas ilustrativas do passo a passo.

Gilberto Gomes28 de novembro de 202616 min de leitura

O terceiro item do mapa de como se treina um modelo é o BigQuery ML, um recurso do banco de dados analítico da Google que permite treinar e usar um modelo com comandos de SQL, a mesma linguagem de consulta que muitos times de dados e de produto já conhecem. Este artigo mostra a ideia, o arquivo de exemplo, cada comando com o código e o resultado, e telas ilustrativas do caminho. Os outros dois itens são Python e scikit-learn e AutoML. Outras plataformas de dados oferecem recursos equivalentes, e o raciocínio vale para elas.

A ideia: o modelo vai até o dado, e não o contrário

No caminho tradicional, os dados saem do banco, vão para um programa em Python, o modelo é treinado e as notas voltam ao banco. No BigQuery ML, tudo acontece no lugar em que a tabela já está: o modelo é criado com um comando e as notas saem em uma nova tabela. Isso reduz a movimentação de dados, o que ajuda em segurança, e permite que quem domina SQL, e a tabela de exemplos da parte técnica 1 costuma ser feita em SQL, chegue ao modelo sem aprender outra linguagem.

O arquivo de exemplo e como ele entra no banco

Para acompanhar, use o mesmo arquivo do artigo de Python e scikit-learn: 2.000 cobranças inventadas, emitidas de março a outubro de 2026. Baixe-o em cobrancas-exemplo.csv. Os campos e o significado de cada um estão descritos naquele artigo; aqui, o que importa é como ele vira uma tabela.

Em quase todo banco de dados analítico, o caminho é o mesmo: criar um conjunto de tabelas (aqui, cobranca), enviar o arquivo e deixar a ferramenta detectar o tipo de cada coluna. A tela abaixo mostra a ideia.

Depois do envio, uma consulta de conferência confirma que a tabela chegou inteira:

-- depois do upload, conferir se a tabela chegou inteira
SELECT COUNT(*) AS linhas, MIN(emissao) AS primeira, MAX(emissao) AS ultima
FROM `meu_projeto.cobranca.cobrancas`;
linhas  primeira    ultima
2000    2026-03-01  2026-10-28

São 2.000 linhas, de março a outubro. As datas precisam chegar como data (DATE), e não como texto, porque a divisão por coorte de emissão depende delas.

Comando 1: CREATE MODEL, o treino

É o comando que treina. Ele pede quatro coisas: o nome do modelo, o tipo de técnica, qual coluna é o alvo e quais exemplos usar. Cada pedaço do código abaixo responde a uma delas.

CREATE OR REPLACE MODEL `meu_projeto.cobranca.modelo_pagamento`
OPTIONS (
  model_type = 'LOGISTIC_REG',
  input_label_cols = ['pago_no_vencimento'],
  data_split_method = 'NO_SPLIT'
) AS
SELECT valor / 100 AS valor_centenas, atrasos_anteriores,
       abriu_mensagem, fim_do_mes, cliente_antigo,
       pago_no_vencimento
FROM `meu_projeto.cobranca.cobrancas`
WHERE emissao < DATE '2026-10-01';
Esta instrução criou o modelo meu_projeto.cobranca.modelo_pagamento.
  • CREATE OR REPLACE MODEL cria o modelo e, se já existir um com esse nome, o substitui. É o que se usa em um retreino.
  • model_type = 'LOGISTIC_REG' escolhe a técnica: a regressão logística, o primeiro modelo recomendado da série.
  • input_label_cols = ['pago_no_vencimento'] diz qual coluna é o alvo, a resposta que o modelo precisa aprender. Todas as outras colunas do SELECT viram sinais.
  • data_split_method = 'NO_SPLIT' manda usar todas as linhas do SELECT no treino. Sem isso, a ferramenta separaria uma parte ao acaso para validar, e queremos o corte por data.
  • O SELECT escolhe os sinais e o alvo, e o WHERE emissao < DATE '2026-10-01' é o corte por coorte de emissão: treina com as coortes de março a setembro (1.750 cobranças) e deixa outubro de fora, para o teste.
  • O valor / 100 deixa o valor em centenas de reais, pela mesma razão do artigo de Python: a escala fica próxima à dos outros sinais.

Observe o que não está no SELECT: o id_cobranca e as datas. Identificadores não ajudam o modelo a generalizar, e a data é usada apenas para o corte.

Comando 2: ML.EVALUATE, a prova

Mede o modelo em cobranças que ele não viu no treino, a coorte de outubro. Note que o WHERE agora é o oposto do treino.

SELECT *
FROM ML.EVALUATE(
  MODEL `meu_projeto.cobranca.modelo_pagamento`,
  (SELECT valor / 100 AS valor_centenas, atrasos_anteriores,
          abriu_mensagem, fim_do_mes, cliente_antigo,
          pago_no_vencimento
   FROM `meu_projeto.cobranca.cobrancas`
   WHERE emissao >= DATE '2026-10-01'));
precision  recall  accuracy  f1_score  log_loss  roc_auc
0.752      0.899   0.732     0.819     0.548     0.739

O que cada coluna diz, nos termos de como saber se o modelo é bom:

  • roc_auc (0,739): o quanto o modelo ordena quem paga acima de quem não paga. É a medida principal.
  • precision (0,752): dos que o modelo disse que pagariam, 75% pagaram.
  • recall (0,899): dos que de fato pagaram, ele encontrou 90%.
  • accuracy (0,732): acertos no total, com o corte padrão de 50%.
  • f1_score e log_loss: resumos que o time de dados costuma acompanhar; quanto menor o log_loss, melhor.

Atenção ao risco de ler demais: como 67,6% das cobranças de outubro pagaram no vencimento, um modelo que sempre dissesse "paga" já teria 68% de acerto. É por isso que a AUC pesa mais que a acurácia, e que o resultado deve ser comparado com a regra simples da área.

Comando 3: ML.PREDICT, a nota de cada cobrança

Aplica o modelo às cobranças e devolve a chance de pagar de cada uma. Aqui está a parte que mais surpreende quem chega do Python: o resultado vem como uma lista de probabilidades, uma para cada resposta possível, e é preciso escolher a que interessa.

SELECT id_cobranca,
       (SELECT prob FROM UNNEST(predicted_pago_no_vencimento_probs)
        WHERE label = 1) AS chance_pagar
FROM ML.PREDICT(
  MODEL `meu_projeto.cobranca.modelo_pagamento`,
  (SELECT id_cobranca, valor / 100 AS valor_centenas,
          atrasos_anteriores, abriu_mensagem, fim_do_mes, cliente_antigo
   FROM `meu_projeto.cobranca.cobrancas`
   WHERE emissao >= DATE '2026-10-01'))
ORDER BY id_cobranca;
id_cobranca  chance_pagar
C1751        0.84
C1752        0.72
C1753        0.81
  • O ML.PREDICT recebe o modelo e a tabela de cobranças a pontuar. Aqui, as de outubro, para comparar depois com o que ocorreu. Em produção, seriam as cobranças abertas.
  • O resultado traz a coluna predicted_pago_no_vencimento_probs, que guarda duas probabilidades: a de label = 0 (não paga) e a de label = 1 (paga).
  • O (SELECT prob FROM UNNEST(...) WHERE label = 1) abre essa lista e pega só a chance de pagar, que batizamos de chance_pagar.

A cobrança C1751, por exemplo, tem 84% de chance de pagar. A partir daí, o resto é o do artigo de Python: dividir em faixas e decidir quem contatar. O resultado costuma ser gravado em uma tabela, para que o painel e a régua o leiam.

Um quarto comando útil: ML.WEIGHTS

Para o gestor, o mais valioso é o porquê. Como a regressão logística é explicável, um comando mostra o peso de cada sinal.

SELECT processed_input, weight
FROM ML.WEIGHTS(MODEL `meu_projeto.cobranca.modelo_pagamento`)
ORDER BY ABS(weight) DESC;
processed_input     weight
atrasos_anteriores  -0.919
abriu_mensagem       0.689
cliente_antigo       0.633
fim_do_mes          -0.286
valor_centenas      -0.121
__INTERCEPT__        1.103

A leitura é a mesma do artigo de Python: o sinal do peso diz o lado, e o tamanho, a força. O __INTERCEPT__ é o ponto de partida. E vale o mesmo cuidado: o peso mostra uma associação nos exemplos, e não uma causa.

Outros tipos de modelo, trocando uma linha

Para testar uma árvore, basta mudar o model_type e repetir os dois comandos seguintes. As técnicas que interessam à cobrança são as já conhecidas da série: a regressão logística e as árvores de decisão, na forma de gradient boosting e de floresta.

A recomendação é a mesma de qualquer caminho: começar pela regressão logística, comparar com a árvore e ficar com a mais simples que bastar.

Vantagens, custo e limites

A grande vantagem é a proximidade com o dado: menos cópias, menos etapas e uma ponte natural entre o time de produto, que costuma entender SQL, e o de dados.

Sobre os números deste artigo: o ambiente em que preparei o material não executa o BigQuery, então os resultados das telas e dos blocos são valores de referência calculados em Python, com a mesma técnica e o mesmo corte, no mesmo arquivo. Na sua execução, a ferramenta pode dar números ligeiramente diferentes, por diferenças de ajuste e de regularização, mas a leitura continua a mesma. As telas são ilustrativas e genéricas, e não capturas do produto.

Se a empresa já usa um banco de dados analítico na nuvem, vale experimentar o recurso equivalente antes de montar um ambiente novo. Se precisa de controle fino sobre o treino, o caminho é o de Python e scikit-learn; se precisa de rapidez de comparação, o de AutoML.

Minha proposta

  • O modelo vai até o dado: treina-se com SQL, dentro do banco.
  • Três comandos bastam: criar, avaliar e pontuar; um quarto mostra os pesos.
  • O corte por coorte de emissão está no WHERE, e é seu trabalho garantir que ele exista.
  • As técnicas são as mesmas da série: regressão logística e árvores.
  • Estime o custo de processamento antes de rodar em larga escala.

Perguntas para a sua equipe

  • Os dados de cobrança já estão em um banco de dados analítico na nuvem?
  • Quem no time escreveria os comandos e quem os revisaria?
  • O WHERE de treino e o de teste separam as coortes de emissão sem se sobrepor?
  • Quanto custaria o processamento de uma rodada de treino?

O que fica

Para quem já vive em SQL, treinar um modelo no banco de dados é o caminho mais curto entre a tabela de exemplos e a primeira pontuação.
